# How a style is packaged: STYLE.md against our look YAML

## Their package

Each of the 66 styles is a folder `styles/<slug>/`:

| File | What it holds |
|---|---|
| `style.json` | Card data: `slug`, `num`, `en`, `cn`, `category_en`, `category_cn`, `film` (demo title), `line` (one sentence on the demo), `line_cn`, `uses` (three jobs, e.g. "Reconstructions; Fact-checks; Incident reports"), `frame_sec` (poster frame), `dur` |
| `STYLE.md` | The invariants: what stays true for every film in the style. 6 to 11 KB, eleven numbered sections (below) |
| `DEMO.md` | Everything about the one demo film: story, shot table with times, score structure, palette and props, end card, build notes, demo-specific pitfalls |
| `demo/` | The demo's source with a one-command `build.sh`, `CREDITS`, and for factual styles `FACTS.md`, `SOURCES.md` and the tools that found the material |
| `poster.jpg`, `<slug>.srt` | Gallery poster and subtitles |

`styles/README.md` is generated from the `style.json` files (`styleboard/build.py`), the same way our
`toolbox/INDEX.md` is generated by `toolbox/index.py`.

The STYLE.md sections, fixed so other guides can point at them:

1. **Essence, and what it is not**: three to five traits that make a frame read as the style in one
   glance, then the styles it is confused with and the line between them.
2. **Materials and rendering**: the physical medium and how code imitates it (layers, blend modes, noise,
   mark stepping), which effects are world-anchored and which are screen-space. Woodcut gives a table of
   knife classes with pixel widths.
3. **Colour logic**: rules, not a palette (how many hues, the ground, what the accent is for, what is never
   coloured); one example palette at most.
4. **Type and subtitles**: licence-free faces, roles and size ranges, where subtitles live in the style's
   world (a print margin, a HUD plate), the reading-time rule.
5. **Motion quality**: frame rate and stepping, easing, weight, how things appear and leave, what never moves.
6. **Camera grammar**: a table of moves, what each expresses, and kinds of moment it can serve; no route,
   no prescribed opening or ending; allowed and forbidden transitions.
7. **Sound palette**: instruments, articulations, modes, foley materials, ambience, silence, mix character,
   voice. No BPM, key or score arc (those are the demo's).
8. **Native moves**: a menu of moments only this medium can do, each with how to build it and "fits
   content like" three examples unlike the demo.
9. **Pitfalls of the medium**: each mistake with its fix.
10. **Engine**: which demo files hold reusable code, their main functions, a minimal example.
11. **Variation space**: what each film decides, then three structures, three openings and three endings,
    all far from the demo.

The split that makes it work: STYLE.md is the language, DEMO.md is one sentence in it. An agent reads
STYLE.md, writes its own treatment, and only then opens DEMO.md, to learn a technique, never the story.

## Our package

One file per look, `looks/<slug>.yaml` (see `looks/README.md`). Public card fields (`slug`, `title`,
`note`, `used`, `cost`, `group`, `order`, `collection`, `clip`, `tall`) and an internal recipe (`status`,
`engine`, `project`, `code`, `rules`, `palette`, `reference`, `proof`, `verdict`, `related`). The project
folder holds the film; some projects carry a look bible (`STORYBOARD-cut.md` for In Her Dream) or build
rules (`docs/WOODCUT_BUILD.md` for Me and Jimi).

## Side by side

| Concern | Theirs | Ours |
|---|---|---|
| What the look is, at a glance | §1 essence, 3-5 traits | `note` (public, one or two sentences) |
| What it is not | §1 "not X, not Y", with the line between | Nothing |
| How to draw it | §2 materials, with numbers | `rules` (short lines), `code.path`, `code.note` |
| Colour | §3 logic, example palette marked as example | `palette` (hex list) plus colour lines in `rules` |
| Type | §4, with sizes and reading time | A line in `rules` when there is one |
| Motion | §5 | Lines in `rules` (on twos, boil) |
| Camera | §6 table of moves | Nothing |
| Sound | §7 palette | Nothing (songs supply it for music videos) |
| Signature moments | §8 native moves, each with "fits content like" | Nothing; Robin's protected moments live in project notes and memory |
| Known failures | §9 pitfalls with fixes | Spread across review-checklist incidents and project notes |
| Code to reuse | §10 engine pointer and minimal example | `code` (path, flag, page, note) |
| Range | §11 three structures, openings, endings | Nothing |
| Jobs it suits | `uses`, three of them | `used` (where it was used, not what it is for) |
| Where it came from | Only in DEMO.md | `reference` (internal) |
| Has it worked? | Nothing: every style is shown, none is judged | `status`, `proof` (renders, PRs, YouTube ids), `verdict` with Robin's or the client's words and a date |
| What it costs | Nothing (everything is code) | `cost`, `group` |

## Reading the difference

Theirs is a teaching document: written so an agent that has never seen the look can make a new film in
it that does not repeat the demo. Ours is a record: written so we can find a look, show it on
novadiem.com, and rebuild it, with proof that it worked for a real client and what Robin said. Each is
missing what the other has.

What their shape catches that ours misses:

- **What it is not.** Robin's "name the look honestly" correction (the shin-hanga section that read as
  vector illustration) is a missing "not flat vector with a texture filter" line. Their woodcut §1 has
  exactly that line.
- **Native moves.** Our best moments (the In Her Dream sun shrinking into the street lamp, the
  cross-stitch heart unpicked and restitched) are what make a look worth reusing, and they live only in
  project files and memory. A builder starting a second film in the look never sees them.
- **Pitfalls with fixes.** Our looks fail the same way twice because the fix lives in a project's
  history (pale detail on cream; boiling hatching; lazily cached strokes that make frames depend on the
  render worker, which their woodcut §9 lists and is the same class of bug as our `scan-every-frame`
incident on More draft 4).
- **Camera and sound.** For explainers and devweb we make the sound; a look that carries a sound palette
  saves the first round of "it sounds like stock".
- **The language / one-film split.** Their rule "read STYLE.md, write your treatment, then open DEMO.md"
  is `fresh-direction-per-video` enforced by the file layout.

What ours has that theirs lacks, and should keep: status and verdict in the client's words, proof links,
cost, and the honest `rejected` status. Their gallery shows 66 styles and judges none.

## Proposal (for Robin; not applied here)

Add four optional recipe fields to `looks/<slug>.yaml`, internal only, never synced to the site. Fill them
when a look is next used, not as a backfill project:

```yaml
not: >-                       # what it is easily mistaken for, and the line
  Not flat vector with a print filter: the marks are carved, so cuts follow the form.
moves:                        # native moves: what it is, how it's built, what it fits
  - name: Block cracks open
    how: <file and function that draws it>
    fits: a reveal; a verdict; a held secret let out
pitfalls:                     # medium failures with their fix
  - Hatching every surface reads as fur; cut the lit edge only.
uses:                         # jobs it would suit, not where it was used
  - a folk tale; a protest song; a labour history
```

`camera` and `sound` can stay in a look's project bible until a look is used for an explainer. `looks/README.md`
would need the four rows added to its recipe table, and the site's `sync-looks` should be checked to
make sure new recipe fields never reach the styles page.
